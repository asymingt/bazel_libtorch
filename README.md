# LibTorch 2.14 for Bazel — from source, hermetic, cross-compiled

This repository is a **staging area for a set of Bazel modules that build
LibTorch 2.14.1 (`pytorch/pytorch@v2.14.1`) from source** with a hermetic LLVM
toolchain and multi-vendor GPU support (`CUDA`, `ROCm/HIP`, `Intel XPU`,
`Vulkan`, and `Apple MPS`). It holds a local Bazel registry
(`bazel_registry.json` + `modules/`) with `@libtorch` and its companion modules,
the smoke and runtime tests that exercise them, and the CI that proves they
build and cross-compile everywhere. The goal is to upstream these modules to the
[Bazel Central Registry](https://registry.bazel.build); until then you can use
them directly from here.

## Why build LibTorch from source?

Existing Bazel integrations download official prebuilt `libtorch` archives or
shell out to CMake via `rules_foreign_cc`. That is convenient, but it quietly
breaks the guarantees Bazel is supposed to give you:

- **Prebuilts assume GCC/libstdc++ on Linux and MSVC on Windows.** The official
  Linux binaries are compiled with GCC against `libstdc++`, and the official
  Windows binaries are compiled with MSVC against `msvcp140.dll`. Link them from
  a Clang/`libc++` toolchain (as any hermetic LLVM setup does) and you are
  mixing two C++ standard libraries and two ABIs in one process — causing
  missing symbol errors on `std::__1::` vs. `std::__cxx11::` or silent
  `std::string`/`std::function`/`std::optional` layout mismatches across every
  `c10::` and `at::` boundary.
- **Prebuilts are not hermetic and lock you into one GPU stack.** Official
  archives are split into separate monolithic downloads per accelerator
  (`cpu`, `cu128`, `rocm6.3`, `xpu`) and expect host-installed toolkits or
  system libraries (`/usr/local/cuda`, `/opt/rocm`, `libgomp`, `libnuma`).
  Reproducible remote execution and multi-vendor GPU builds are off the table.
- **Cross-compilation is impossible.** A downloaded archive targets one
  OS/architecture; targeting another means a different download, a different
  sysroot, and on macOS and Windows a non-hermetic native SDK.

Building LibTorch — and its GPU device kernels and link-time driver/runtime
stubs — from source inside the Bazel action graph with one hermetic Clang
toolchain fixes all three: a single Clang/`libc++` ABI end to end, nothing read
from `/usr` or `/opt` at build time, hardware drivers loaded dynamically at run
time, and `--platforms=...` as the only difference between a Linux, macOS or
Windows binary.

## Try it now

Point Bazel (**9.0 or newer** — `rules_cc` ≥ 0.2.21, which the hermetic LLVM
toolchain depends on, needs Bazel 9's C++ runtime toolchain type) at the GitHub
Pages mirror of this registry, ahead of the BCR, in your `.bazelrc`:

```
common --registry=https://asymingt.github.io/bazel_libtorch/
common --registry=https://bcr.bazel.build
```

Then depend on `@libtorch` like any other module:

```starlark
# MODULE.bazel
bazel_dep(name = "llvm", version = "0.8.25")      # hermetic toolchain
bazel_dep(name = "rules_cuda", version = "0.3.0") # CUDA rules & redist
bazel_dep(name = "libtorch", version = "2.14.1")
register_toolchains("@llvm//toolchain:all")
```

```starlark
# BUILD.bazel
load("@rules_cc//cc:defs.bzl", "cc_binary")

cc_binary(
    name = "app",
    srcs = ["main.cc"],
    deps = ["@libtorch//:torch"],
)
```

Cross-compile the same target for any supported platform with nothing but a
flag:

```
bazel build //:app --platforms=@llvm//platforms:macos_arm64
bazel build //:app --platforms=@llvm//platforms:windows_amd64
bazel build //:app --platforms=@llvm//platforms:linux_arm64_gnu.2.34
```

### Toolchain requirements

The overlays assume Clang with `libc++` on every platform (on Windows, a
MinGW-UCRT sysroot targeting `x86_64-w64-windows-gnu` and
`aarch64-w64-windows-gnu`) and compile with `-std=gnu++20`. MSVC
(`cl.exe`/`clang-cl`) is not required or supported. This workspace's `.bazelrc`
also sets flags the build relies on: `--features=system_include_paths`,
`--@llvm//config:experimental_stub_libgcc_s=False`,
`--repo_env=CUDA_COMPILER_USE_CC_TOOLCHAIN=true`,
`--@rules_cuda//cuda:compiler=clang`, and
`--@rules_cuda//cuda:copts=-D_ALLOW_UNSUPPORTED_LIBCPP` (the CUDA headers
otherwise reject `libc++` on x86). We recommend registering the hermetic
`@llvm` toolchain as shown above.

## How this differs from other Bazel + LibTorch projects

- **LibTorch is built from source, not downloaded.** Every `c10`, `ATen`, and
  `torch` library, Python codegen step (`torchgen` and `gen_autograd`), and GPU
  device kernel is compiled in the Bazel action graph from hash-pinned upstream
  source archives. No prebuilt SDK download, no `rules_foreign_cc` CMake wrapper.
- **Hermetic GPU builds via link-time driver stubs.** Device kernels are
  compiled hermetically with Clang (`NVPTX` for CUDA, `AMDGPU` for ROCm/HIP,
  SPIR-V for Vulkan, Objective-C++ for Metal/MPS), while host runtime/driver
  boundaries link against lightweight symbol-stub DSOs/import libraries
  (following the `libglvnd` pattern from `qt_bazel_workspace`). Linux CI builds
  every GPU backend without needing physical GPU hardware or host drivers
  installed, and binaries bind to the real hardware drivers at runtime.
- **Cross-compilable across 6 platforms.** One Linux host can produce
  Linux/macOS/Windows binaries for `x86_64` and `arm64`.
- **No patches to PyTorch.** `@libtorch` is the pristine upstream `v2.14.1`
  tarball plus a registry overlay (`BUILD.bazel`, `MODULE.bazel`, config/codegen
  `.bzl` files).

## Layout

| Path | Purpose |
| --- | --- |
| `bazel_registry.json`, `modules/` | The Bazel registry, published to GitHub Pages on every merge (`.github/workflows/ci.yaml`). |
| `libtorch.txt` | Target pattern list (`//...` plus `@<module>//...` for all local registry modules), selected by `--config=libtorch`. |
| `tests/` | Smoke and runtime tests per LibTorch subsystem and GPU backend, run natively and cross-compiled by the CI matrix. |
| `design/` | Architecture and engineering plans (`DESIGN.md`, `PHASE1.md` ... `PHASE5.md`). |
| `patches/` | Patches for third-party BCR modules, one directory per module, applied via `single_version_override`. See below. |
| `.github/workflows/` | CI: `pull_request.yaml` (build/test matrix), `bazel.yaml` (one host/target job), `cache_cleanup.yaml`, `ci.yaml` (registry publishing). See [Continuous integration](#continuous-integration). |
| `.bazelrc` | Toolchain flags, `--config=libtorch`, `rules_cuda` flags, and sanitizer configs. No platform is pinned, so `bazel test //...` builds natively on any supported host; cross-compile by passing `--platforms=@llvm//platforms:<os>_<arch>` explicitly. Warnings from third-party (non-LibTorch) dependencies are silenced so that LibTorch's own stand out. |
| `bazel_downloader.cfg` | Download mirrors for upstream tarballs of BCR modules we cannot annotate with `mirror_urls`. |

## Continuous integration

`pull_request.yaml` runs on every pull request and on every push to `main`:

1. **Native** (6 jobs): build `--config=libtorch` (`//...` and every `@<module>//...`) and test `//...` on each of Linux, macOS and Windows, `x86_64` and `arm64`.
2. **Cross** (30 jobs): every host cross-compiles `--config=libtorch` for every other platform. These only start once all native jobs are green.
3. **`last_rc`**: repeats the native and cross matrix with Bazel's latest release candidate. Its failures are reported but never fail the run.
4. **Status** (`main` only): publishes one [build status](#build-status) matrix per Bazel version to the `status` branch.

Each job keeps a Bazel disk cache in GitHub's Actions cache, keyed by host,
target and commit and pruned to what the build used. GitHub lets every pull
request restore caches saved on `main`, but never another pull request's, so
`main` seeds the shared caches (runs on `main` are never cancelled by a later
merge, and only the 9.x stage saves). A pull request saves its own caches for
quick re-runs, and `cache_cleanup.yaml` deletes them once it is merged or
closed.

## Patches to third-party modules

A few *third-party* Bazel modules are patched via `single_version_override` in
`MODULE.bazel`, with the patch files kept under `patches/<module>/`. These only
apply inside this workspace (overrides are not part of the published registry);
each one is a stopgap we intend to drop once the fix lands upstream.

| Module | Patch | Why |
| --- | --- | --- |
| `llvm` | `patches/llvm/*.patch` | Toolchain fixes for the hermetic LLVM module: header search paths, sanitizer runtimes, Windows `@params` files, de-duplicated `-rpath` entries, quiet MinGW `.def` preprocessing, extracting the `System/Cryptexes` targets of macOS SDK frameworks, and building the static Windows `libc++abi` without `dllexport` annotations (otherwise every MinGW DLL re-exports the `std::` exception classes). |
| `rules_cuda` | `patches/rules_cuda/multiplatform_redist.patch` | Map `linux-arm64` to `linux-sbsa`, gracefully disable `@cuda` on macOS hosts where NVIDIA does not publish host tools, and emit `select()` aliases across `linux-x86_64`, `linux-sbsa`, and `windows-x86_64` in `@cuda//BUILD` so CUDA targets can be cross-compiled across OS/CPU pairs. |
| `gflags` | `patches/gflags/windows_platform.patch` | Selects gflags' Windows sources and defines by `@platforms//os:windows` instead of the legacy `--cpu=x64_windows` value, which MinGW builds never set (they failed on `<fnmatch.h>`). |
| `cpuinfo` | `patches/cpuinfo/windows_arm64_header.patch` | Lists the private `windows-arm-init.h` header of its Windows-on-Arm backend in `srcs`, which `windows_arm64` builds need. |
| `rules_perl` | `patches/rules_perl/windows_arm64_emulated_x86_64.patch` | Registers a `windows`/`arm64` Perl toolchain that reuses the hash-pinned `x86_64` Strawberry Perl archive under Windows-on-Arm emulation when building on `windows-11-arm` runners. |
